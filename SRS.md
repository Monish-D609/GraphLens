## 1. Introduction

### 1.1 Purpose
This document specifies the functional and non-functional requirements for GraphLens, a retrieval-augmented question-answering system that combines vector similarity search with an entity–relationship graph derived from the same document corpus.

### 1.2 Scope
GraphLens ingests a document corpus, chunks it, extracts entities and the relationships between them, embeds the chunks, and answers natural-language queries using a hybrid of vector retrieval and graph traversal. Answers are generated by an LLM grounded in the retrieved context and include citations to source documents. The system supports a retrieval-mode toggle between vector-only and graph-augmented retrieval.

### 1.3 Definitions

| Term | Definition |
|---|---|
| Chunk | A contiguous segment of a source document, the unit of retrieval |
| Entity | A named element of the domain (e.g. `PaymentService`, `UserModule`) |
| Relationship | A directed, typed link between two entities (e.g. `PaymentService --depends on--> UserModule`) |
| Graph | The set of entity nodes and relationship edges extracted from the corpus |
| Vanilla retrieval | Vector similarity search only |
| Graph-augmented retrieval | Vector similarity search merged with graph-traversal results |
| Hop | One traversal step along an edge from a given node |

## 2. Overall Description

### 2.1 System Context
GraphLens is a self-contained application consisting of an ingestion pipeline, two storage components (a vector store and a graph store), a retrieval layer, and a generation layer, accessed through a query interface. It depends on an external embedding model and an external LLM.

### 2.2 System Architecture

```
Documents
   |
   v
[1] Ingestion & Chunking
   |
   +---------------------------+
   |                           |
   v                           v
[2] Entity & Relationship   [3] Embedding
    Extraction                  |
   |                            v
   v                        Vector Store
Graph Store                     |
   |                            |
   +------------+---------------+
                |
                v
        [4] Hybrid Retrieval
          (merge + dedupe)
                |
                v
        [5] Answer Generation
            (with citations)
```

### 2.3 Design Constraints
- No dedicated graph database is required. The graph may be stored in SQLite, an in-memory graph library (e.g. NetworkX), or a JSON adjacency structure.
- The system is single-user and runs locally.
- Extraction is scoped to a single chosen domain, not open-domain.

### 2.4 Assumptions and Dependencies
- The corpus is text-based and available locally.
- Network access to an embedding model and an LLM is available.
- Entity names in the corpus are reasonably consistent in spelling and casing.

## 3. Functional Requirements

### FR-1 Document Ingestion
| ID | Requirement |
|---|---|
| FR-1.1 | The system shall read documents from a configured corpus directory. |
| FR-1.2 | The system shall support plain-text and Markdown source files. |
| FR-1.3 | The system shall record, for each document, its file path and identifier. |
| FR-1.4 | The system shall skip unreadable or unsupported files and log them without aborting ingestion. |

### FR-2 Chunking
| ID | Requirement |
|---|---|
| FR-2.1 | The system shall split each document into chunks of a configurable size. |
| FR-2.2 | The system shall apply a configurable overlap between adjacent chunks. |
| FR-2.3 | Each chunk shall retain metadata identifying its source document and position within it. |
| FR-2.4 | Each chunk shall be assigned a unique, stable identifier. |

### FR-3 Entity and Relationship Extraction
| ID | Requirement |
|---|---|
| FR-3.1 | For each chunk, the system shall extract zero or more entities. |
| FR-3.2 | For each chunk, the system shall extract zero or more directed, typed relationships between extracted entities. |
| FR-3.3 | The system shall support rule-based extraction where the corpus structure permits deterministic parsing. |
| FR-3.4 | The system shall support LLM-based extraction for unstructured prose. |
| FR-3.5 | The system shall normalise entity names so that surface variants resolve to a single node. |
| FR-3.6 | Each extracted edge shall record the chunk identifiers it was derived from. |
| FR-3.7 | The system shall persist the resulting graph to disk. |

### FR-4 Embedding and Vector Storage
| ID | Requirement |
|---|---|
| FR-4.1 | The system shall generate an embedding vector for each chunk. |
| FR-4.2 | The system shall store each embedding together with its chunk text and metadata. |
| FR-4.3 | The vector store shall persist across runs without requiring re-ingestion. |

### FR-5 Vector Retrieval
| ID | Requirement |
|---|---|
| FR-5.1 | The system shall embed an incoming query using the same model used for chunks. |
| FR-5.2 | The system shall return the top-K most similar chunks, K configurable. |
| FR-5.3 | Each returned chunk shall carry its similarity score and source metadata. |

### FR-6 Graph Retrieval
| ID | Requirement |
|---|---|
| FR-6.1 | The system shall identify entities referenced in the query and resolve them to graph nodes. |
| FR-6.2 | The system shall traverse from each matched node to its neighbours, to a configurable depth of 1 to 2 hops. |
| FR-6.3 | The system shall retrieve the chunks associated with the traversed nodes and edges. |
| FR-6.4 | If no query entity resolves to a node, graph retrieval shall return an empty set without error. |

### FR-7 Hybrid Merge
| ID | Requirement |
|---|---|
| FR-7.1 | The system shall merge vector and graph result sets into a single ordered context set. |
| FR-7.2 | The system shall deduplicate chunks appearing in both sets. |
| FR-7.3 | The system shall cap the merged context at a configurable size limit. |

### FR-8 Answer Generation
| ID | Requirement |
|---|---|
| FR-8.1 | The system shall generate an answer using an LLM prompted with the merged context and the query. |
| FR-8.2 | The answer shall be grounded in the provided context; the model shall be instructed not to answer from outside it. |
| FR-8.3 | The answer shall cite the source documents of the chunks it relied on. |
| FR-8.4 | When the context does not support an answer, the system shall state that rather than fabricating one. |

### FR-9 Retrieval Mode Toggle
| ID | Requirement |
|---|---|
| FR-9.1 | The system shall provide a toggle between vanilla and graph-augmented retrieval. |
| FR-9.2 | In vanilla mode, graph retrieval shall be bypassed entirely. |
| FR-9.3 | The system shall report which mode produced a given answer. |
| FR-9.4 | The system should display the entities and edges used in a graph-augmented answer. |
| FR-9.5 | The system may run both modes on one query and present the results side by side. |

## 4. Non-Functional Requirements

| ID | Category | Requirement |
|---|---|---|
| NFR-1 | Performance | Query response time shall not exceed 10 seconds for a corpus of up to 1,000 chunks. |
| NFR-2 | Performance | Ingestion of the full corpus shall complete in a single unattended run. |
| NFR-3 | Reliability | A failure in extraction for one chunk shall not abort the ingestion pipeline. |
| NFR-4 | Persistence | Vector store and graph store shall survive process restart. |
| NFR-5 | Configurability | Chunk size, overlap, top-K, traversal depth, and context cap shall be configurable without code changes. |
| NFR-6 | Traceability | Every answer shall be traceable to the chunks and source documents used to produce it. |
| NFR-7 | Portability | The system shall run locally on a single machine with no server infrastructure. |
| NFR-8 | Maintainability | Retrieval modes shall be separable so that the vanilla path can run independently of the graph components. |

## 5. External Interfaces

| Interface | Description |
|---|---|
| Corpus directory | Local filesystem path containing source documents |
| Embedding model API | Converts text to vectors; same model for chunks and queries |
| LLM API | Used for relationship extraction (where rule-based parsing is insufficient) and for answer generation |
| Query interface | Accepts a natural-language query and a retrieval mode; returns an answer, citations, and retrieval trace |

## 6. Acceptance Criteria

| ID | Criterion |
|---|---|
| AC-1 | A defined set of relationship queries returns correct answers in graph-augmented mode. |
| AC-2 | The same queries in vanilla mode return demonstrably weaker or incorrect answers, and the difference is observable in the retrieved context. |
| AC-3 | Factual lookup queries perform no worse in graph-augmented mode than in vanilla mode. |
| AC-4 | Every answer includes at least one resolvable citation. |
| AC-5 | Ingestion of the full corpus completes without manual intervention. |
| AC-6 | Toggling retrieval mode changes the retrieval path and is reflected in the reported trace. |
